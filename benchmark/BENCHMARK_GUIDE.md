Each `test_cases` record carries `case_id`, `task_type ∈ {annotation, rca, qa_mcq}`, `source`, `input`, `expected_*`, optional `acceptable_answers`, and (for the 33 qa_mcq cases) an `excluded_reason` field. The 41 Chinese RCA cases retain `task_type=rca` but receive `correct=null` at scoring time (set by the runner / `rescore_ours_with_sota_eval.py`).

### 5.2 Eval denominator semantics (critical)

Per `final/docs/METHODOLOGY.md` §2 + §6:

```
total_records = 218 (annotation) + 180 (rca) + 33 (qa_mcq) = 431
ann_eval       = all 218 annotation records
rca_eval       = 180 rca records − 41 Chinese-language (correct=null) = 139 evaluable
overall_eval   = 218 + 139 = 357

NEVER divide RCA by 213 or 180 in published numbers. ALWAYS 139.
```

The `qa_mcq` cases are NOT counted in any published accuracy — they were over-included during dataset curation when the Stage-2 LLM judge silently fell back from Bedrock Claude Haiku to local Qwen3-4B-Instruct and accepted 33 CompTIA-style MCQ knowledge questions as `task_type=rca`. The D-1 audit (session 17) re-labeled them as `qa_mcq` with `excluded_reason="MCQ knowledge format ..."`. See BUG_HISTORY footnote D-1.

### 5.3 Candidates

The three `intermediate/candidates/*.jsonl` files are the **vetted mining outputs** that landed in `benchmark_431_seed42.json`:

- `apache_candidates.jsonl`: byte-identical to the raw mirror (SHA-12 `268999cfb202`). Produced by `prep/mine_apache.py` clustering Loghub Apache by EventTemplate, sampling half ERROR-level + half NOTICE-level.
- `openssh_candidates.jsonl`: byte-identical to raw mirror (SHA-12 `2794d6e92224`). Produced by `prep/mine_openssh.py` brute-force-burst detection (3+ "Failed password" from same IP within 60 s).
- `opseval_remine.jsonl`: **non-identical** to the raw `opseval_remine_s2.jsonl` (SHA-12 `15d47964b8de` here vs `b9396a58173d` in raw); the raw `_s2` is an older stage-2 variant from the mining iteration history. The intermediate copy is the version that landed in the paper dataset.

**Record schema** (verified at this dir, post-D-1 + post-CRIT-C2):

```python
# results_sota_eval_431.json: list of 431 records
{
  "case_id":       "ANN_107" | "RCA_OPSEVAL_RM_022" | ...
  "task_type":     "annotation" | "rca" | "qa_mcq",
  "source":        "loghub_bgl" | "lemma_rca_cloud" | "opseval_remine_Wired Network" | ...,
  "model_response": <stringified JSON or prose>,
  "expected":       <dict or string>,
  "correct":        True | False | None,    # None = excluded (Chinese-lang RCA or qa_mcq)

  "eval_method":    "sota_substring",
  "bert_f1":        float (D-6 recompute)
}
```

`results.json` carries additional rich-eval columns: `cosine_similarity`, `term_overlap`, `inference_latency_ms`, `model_used`, and runner.py's `correct` flag (which is BROKEN in 7 of 8 ablation configs — see §6.2 below).

**Why two `correct` flags exist**: see §11 (authoritative numbers) and `final/docs/CURRENT_RUNS.md` §2b. The runner.py rich-eval over-credits (~13-18pp inflation on RCA via rule_score giving partial credit to literal-opposite answers) and under-credits on no-prompt configs (47 false negatives on `no_constitutional` because runner can't parse prose without JSON). The matched/SOTA strict-substring eval is the only valid cross-config / cross-system metric.
